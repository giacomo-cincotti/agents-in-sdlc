プロジェクトに小さな機能を追加しましたが、大きな変更にはより堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。ここから数回のレッスンで、Issue を起点に新機能を作り、コードと動作を検証して、プロジェクトにマージするという、一般的なエージェント主導の開発プロセスを実践します。

> [!NOTE]
> 機能のワークフローでは同じセッションを続けて使用します。通常はファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは中心的な概念に集中できるよう手順を短縮します。

このレッスンでは、次の内容を学習します。

- GitHub Issue から新しいエージェントセッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードで機能を実装する。
- コードをレビューする。
- ブラウザーキャンバスで機能を手動検証する。

以降のレッスンでは、この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが充実し、訪問者がカテゴリーとパブリッシャーでゲームを絞り込める機能が必要になりました。バックログの Issue には機能が記載されていますが、カテゴリーの組み合わせ方など、コーディング前に合意が必要な詳細があります。Plan モードで決定事項を整理してから、範囲を限定した実装を Autopilot に承認します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローに従います。

1. 必要な作業の詳細が記載された Issue を開く。
2. 構築する内容の計画を立てる。
3. コードを構築してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. pull request (PR) を作成する。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージする。

> [!NOTE]
> 正確な手順はチームや Organization によって異なりますが、多くの場合は上記の流れを基にしています。

この標準的なアプローチを守ることで、AI が生成したコードが要件を満たし、人間が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**はエージェントの自律性を制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律してコードを作成し、テストを実行して、入力を待たずに反復します。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** の下にある Tailspin Toys リポジトリ フォルダーを選び、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** Issue を開きます。これはテンプレートに含まれる Issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数カテゴリーをどう組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクト既存のツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。実装とテストに範囲を絞り、品質ワークフローを終えるまで PR は作成しません。計画の修正は承認前に依頼し、後の検証に使えるよう Issue の URL と合意した詳細を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認によってモードが切り替わると決めつけず、モード表示が **Autopilot** になっていることを確認してください。

Copilot は承認済みの計画に沿って実装を開始し、コードの生成やテストを行いながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して問題がないことを確かめましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、結果を Issue と承認した詳細に照らし合わせます。変更が既存のリポジトリ指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認してください。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択して結果を確認します。フィルターを解除し、パブリッシャーを選択して結果を確認します。
4. カテゴリーとパブリッシャーを組み合わせ、結果を Issue と承認した計画に照らし合わせます。複数カテゴリーに対応する場合は、合意した組み合わせ方も検証します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、一覧全体に戻ることも確認します。
6. 確認が終わったら、次のプロンプトでこのセッションが起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにセッションを保持する

フィルター機能の PR はまだ作成またはマージしないでください。このセッション、worktree、ブランチはレッスン 4 から 8 まで使用します。次はフィルターコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後、セッションはそのまま待機させ、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

異なるエージェントモードを使用して、機能を構築およびレビューしました。このレッスンでは、次の作業を行いました。

- GitHub Issue から新しいエージェントセッションを開始した。
- **Plan** モードで要件を定義した。
- **Autopilot** モードを使用して機能を実装した。
- コードをレビューした。
- ブラウザーキャンバスで機能を手動検証した。
